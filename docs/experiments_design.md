# eZmanbo 实验设计方案

> 本文档说明 eZmanbo 系统各项实验的设计依据、测试数据构建方式、评估指标、支撑的系统贡献点，以及预期产出的图表。所有实验均可在当前系统上直接运行，无需外部基准数据集。

---

## 一、测试数据说明

当前没有公开的电子元器件智能选型基准数据集。本系统的测试数据采用以下策略构建：

- **约束解析测试集**：人工编写覆盖多种自然语言表达风格的需求句，由团队成员独立标注各字段的标准值作为真实标签（ground truth）。
- **MPN 可验证性测试**：运行真实查询，以 eZ-PLM 数据库的可查询性作为"可验证"的判断依据。
- **安全约束核查测试**：从 eZ-PLM 数据库中收集已知处于 EOL/Obsolete 状态的器件、已知无 AEC-Q100 认证的器件，构造具有明确违规标签的测试候选集。
- **多轮约束累积测试**：人工设计多轮对话脚本，参数分散在3–5轮中提供，分别在有/无累积机制两种条件下运行系统，记录对话轮数和重复追问情况。

## 二、实验一：自然语言约束解析准确率

### 支撑贡献
需求解析是整个选型流程的入口，其准确率直接决定候选搜索质量，支撑**贡献1（数据接地候选生成）**和**贡献4（多轮约束累积）**。

### 测试集构建
手工编写 **120 条**需求句，覆盖以下变体：
- **电压表达方式**：数值+单位直接写（"12V"）、中文描述（"十二伏"）、隐含（"给锂电池供电"≈3.7V）
- **电流表达方式**：安培（"2A"）、毫安（"500mA"）、隐含大小（"小电流"）
- **拓扑表达**：英文术语（"Buck"）、中文（"降压"）、描述性（"12V降到5V"）
- **等级表达**：英文（"automotive"、"AEC-Q100"）、中文（"车规"、"工业级"）、温度范围描述（"-40到125度"）
- **混合长句**：同时含多个约束的完整描述句

每条句子标注以下字段的真实值：`input_voltage_nominal_v`、`output_voltage_v`、`output_current_a`、`topology`、`grade`、`temperature_min_c`、`temperature_max_c`。字段值为 null 时视为该句不包含该参数（正确输出也应为 null）。

### 评估指标
- **字段级准确率**：对每个字段单独计算提取正确率（数值字段允许 ±5% 误差）
- **完整句准确率**：所有字段均正确提取的句子占比
- **误提取率**：将 null 字段错误提取为非 null 值的比率

### 预期图表
- **图1**：各字段解析准确率柱状图（横轴：7个字段，纵轴：准确率%）
- **表1**：典型错误案例分析（输入句 / 错误输出 / 正确值 / 错误原因分类）

## 三、实验二：推荐型号可验证性对比

### 支撑贡献
直接验证**贡献1的核心主张**：eZmanbo 输出的 MPN 100% 可在 eZ-PLM 中查询；纯 LLM 推荐的 MPN 大量无法核实。

### 测试方法
选取 **50 条**覆盖不同需求场景的选型请求（降压/升压/LDO，不同电压电流组合，工业级/商业级），分别用以下两种方式获取推荐结果：

**方法 A（eZmanbo）**：通过系统完整流程，记录最终推荐列表中的所有 MPN。

**方法 B（纯 LLM 基线）**：将相同的自然语言需求直接发送给 Claude/GPT-4，prompt 格式为"请推荐5个满足[需求]的[类型]器件，给出具体型号"，记录其输出的所有 MPN。

**可验证性判断**：对两种方法输出的所有 MPN，通过 eZ-PLM 关键词搜索接口尝试查询，能够精确匹配（型号字符串完全一致）的计为"可验证"。

### 评估指标
- **MPN 可验证率**：可在 eZ-PLM 中精确查到的 MPN 占推荐总数的比例
- **平均每次查询的可验证推荐数**

- **表2**：LLM 基线输出中不可验证 MPN 的典型样例（型号 / 需求场景 / 查询结果）

## 四、实验三：安全约束核查有效性

### 支撑贡献
验证**贡献2的安全性主张**：对于不满足工程安全条件的候选，系统应实现零漏放（zero false negative）。

### 测试集构建
从 eZ-PLM 平台收集以下已知违规候选，构建测试集（目标 **≥60 个违规候选**）：
- **G3 等级违规**：已知无 AEC-Q100 认证的器件（配合车规需求查询）
- **G4 生命周期违规**：已知处于 EOL、Obsolete 或 NRND 状态的器件
- **G2 温度违规**：温度范围明确不覆盖需求温度区间的器件（如 -20~85°C 的器件用于 -40°C 最低温需求）
- **G1 电气边界违规**：输出电流上限低于需求电流的器件

测试流程：将上述已知违规器件注入候选列表，运行安全约束核查模块，记录每个违规候选的判定结果。

### 评估指标
- **漏放率（False Negative Rate）**：违规候选被错误放行的比例（目标值：0%）
- **过滤率**：各规则（G1–G6）各自拦截的候选数量分布

### 预期图表
- **图3**：各安全规则拦截数量分布图（按 G1–G6 分类的柱状图）
- **表3**：典型拦截案例（器件 MPN / 需求场景 / 违规规则 / 判定原因）

## 五、实验四：多轮约束累积效果

### 支撑贡献
验证**贡献4（服务端多轮约束累积）**：有累积机制的系统比无累积机制的系统需要更少交互轮数完成选型，且不重复追问已提供的参数。

### 测试集构建
设计 **30 组**多轮对话脚本，每组包含 3–5 轮用户输入，参数分批提供。脚本覆盖：
- 顺序分批（第1轮电压，第2轮电流，第3轮等级）
- 乱序补充（第1轮电流，第2轮等级，第3轮补充电压）
- 指代性补充（"就是刚才说的那个电压"）
- 部分参数省略（用户不提供温度范围，直接说"工业级"）

分别在以下两种条件运行：
- **条件 A（有累积）**：启用 constraint_store 服务端状态
- **条件 B（无累积）**：每轮独立处理（模拟无状态系统）

### 评估指标
- **平均触发选型所需轮数**：从对话开始到系统触发选型流程的平均轮数
- **重复追问率**：系统询问用户已在前轮提供过的参数的次数比例
- **约束完整性**：选型触发时，已累积的约束字段数量

- **图5**：有/无累积机制下重复追问次数分布（箱线图或柱状图）
- **表4**：典型多轮对话案例（展示约束逐轮累积的过程）

## 六、实验五：响应时延与缓存收益

### 支撑贡献
验证系统的工程可用性，测量缓存机制和并发检索对响应时间的影响。

### 测试方法
- **缓存收益**：对 50 条查询进行两轮测试，第一轮为冷启动（无缓存），第二轮为热启动（语义缓存命中率 ≥ 0.95 的相似查询）。
- **并发检索收益**：对相同的 30 条查询，分别在并发检索（asyncio.Semaphore 并发4）和串行检索（无并发）两种条件下运行，记录候选搜索阶段耗时。

### 评估指标
- **冷/热端到端响应时间**（中位数和 P90）
- **候选搜索阶段耗时**：并发 vs 串行
- **语义缓存命中率**：对相似查询（语义相似度 ≥ 0.95）的命中比例
